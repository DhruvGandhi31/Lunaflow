# M4 — Traffic + Measurement Harness

**Status: PASS** (Nov 2026, WSL2).
Smoke test (`m4_smoke`, 5 nodes): 30/30 tagged bundles delivered across the coverage gap. The relay occupancy curve shows the bundles filling the relay, waiting out the gap, then draining.
Overflow calibration (`m4_overflow`, 5 nodes): 4.5 MB offered to a relay capped at 2 MB. The relay's UDP induct died at T0+31. Delivery was 58/90: every bundle sent up to T0+31 was delivered, and every bundle sent after it was lost.

**Goal:** turn "run a scenario" into "run a scenario and get numbers". The harness drives tagged traffic, samples storage, scrapes ION's logs and counters, and writes CSVs and a JSON summary that M5–M7 plot and compare.

## 2. Running it

```bash
cd ~/lunaflow/scripts
python3 genscenario.py ../scenarios/m4_smoke.json       # -> ~/testbed/m4_smoke
python3 run_experiment.py ~/testbed/m4_smoke            # ~3 min, prints summary.json
#   --out DIR    results dir        --lead S   T0 = contact load + S (default 15)
#   --keep       leave nodes up     --seed N   RNG seed for send-time jitter
```

`run_experiment.py` calls `start_all.sh` itself. Don't boot the network beforehand. As before, `killm f` kills every ION node on the host.

## 3. The traffic section (scenario JSON)

```json
"traffic": {
  "end": 160,              // measure until T0+end (default: scenario duration)
  "sample_interval": 2,    // storage sampling period, seconds
  "monitor": [20],         // nodes to sample (default: all)
  "flows": [
    {"srcs": [101, 102, 103], "dst": 30, "start": 12, "count": 10,
     "interval": 1.0, "size": 20000, "ttl": 3600, "class": "bulk", "jitter": 0}
  ]
}
```

Each `(flow, src)` pair gets one sender thread. Bundle *k* is scheduled at `T0 + start + k·interval` (± jitter). `size` is the exact payload size, from 64 to 60000 bytes. The UDP convergence layer's hard limit is 65535 bytes including BP headers.

## 4. How each measurement works (and why it works that way)

All of these mechanisms were checked against the ION source (`ION-DTN` @ `e2880b3`) and confirmed with probe runs.

| Measurement | Mechanism | Why not the obvious approach |
|---|---|---|
| Bundle identity | Each payload is `LF1\|src\|seq\|class\|t_sent_ms\|` padded to `size`. | `bpsource` sends anonymously (source EID `dtn:none`), so the payload must carry the source. |
| Sending | One `bpsource <dst> "<payload>" -t<ttl>` call per bundle. | Interactive `bpsource` (stdin) splits long lines into chunks of about 256 bytes. |
| Source backpressure | `send_s` column, the duration of the `bpsource` call. | `bpsource` **blocks** (no loss) while its node's outbound storage is full. |
| Delivery | `bprecvfile ipn:<dst>.1` writes each payload to `testfileN`. The harness polls, parses the tag, uses the file's mtime as `t_delivered`, then deletes the file. | `bpsink` prints a payload only if it is under 80 bytes (`char content[80]`). |
| Storage occupancy | `ionadmin` running a one-line `m usage` script in each node directory. It reports inbound and outbound heap and file MB at 0.01 MB resolution. | `bplist` hex-dumps every payload, which is slow at scale. Killing it mid-call left an SDR transaction open and wedged a node during development. |
| Node counters | `bpstats` on every node at the end, then the last `[x] src/fwd/xmt/rcv/dlv/rfw/exp` lines are parsed from `ion.log`. Each line has per-priority (0/1/2) and total counts and bytes. | ION has no "discarded" category in this report. |
| Events | The harness tails every `ion.log`. `Can't acquire bundle` maps to `induct_failure`, `[?]` to `warning`, `at line` to `error`. | |

Bundle `status` values: `DELIVERED` · `DELIVERED_LATE` (after TTL) · `UNDELIVERED` · `SEND_FAILED` · `SEND_BLOCKED` (still blocked at end of run) · `NOT_SENT`.

**Metrics in `summary.json`:**
- `delivery_ratio` = DELIVERED ÷ generated, overall and broken down by class and by source.
- Latency mean, p50, p95 and max.
- `storage_peak`: peak MB per node, compared with its configured `cap_mb`.
- Event counts.
- `induct_failures`: when and where a receiver died.

## 5. Storage caps: what actually limits a relay (correction to M3)

M3 treated `heap_words` as the relay storage cap. **It isn't.** The ION source shows why:

1. **Large bundles bypass the heap by default.** A bundle received over UDP is stored in the SDR heap only if it is ≤ `maxAcqInHeap` = **560 bytes** (`libbpP.c:1764`). Anything larger goes to **file space**, whose limit defaults to **1 TB** (`zco.c:172`). With realistic bundle sizes the relay never fills, whatever `heap_words` is set to.
2. **ION reserves most of the heap.** It sequesters 60% of the heap (`ION_SDR_MARGIN` 20 + `ION_OPS_ALLOC` 40). Inbound and outbound bundles each get half of the remaining 40% by default. The old `heap_words` 250000 (2 MB) therefore meant only 0.4 MB inbound.
3. **Bundles live in two pools.** A received bundle sits in the **inbound** pool. Once forwarding queues it for a contact, it moves to the **outbound** pool.

So `buffer_mb: B` on a node now generates:

```
node.ionrc:  m inbound  ceil(B/2) 0     # inbound heap limit MB, file limit 0
             m outbound floor(B/2) 0
node.bprc:   m heapmax 65000            # every UDP bundle acquired into heap
heapWords := max(heap_words, B·1e6·1.25 / 0.40 / 8)   # so the limits are accepted
```

**Measured behaviour (`m4_overflow`, B = 2 → 1 + 1 MB):**

```
t      in_heap  out_heap  total
14.0   0.00     0.36      0.36    bundles arrive, are queued for 20->30, move to outbound
24.0   0.00     1.96      1.96
26.0   0.26     2.01      2.27    outbound stops growing; inbound starts filling
32.0   0.97     2.01      2.98    inbound at its 1 MB limit -> next bundle has no space
```

- The **inbound limit is enforced exactly.**
- The outbound pool plateaued at about 2.0 MB, even though `m outbound 1` was set and acknowledged in `ion.log`. I haven't found in the source why it plateaus there.
- **Don't assume capacity from `buffer_mb`; calibrate it from `buffer.csv`.** The effective relay capacity in this configuration is about 3 MB.

## 6. Finding: on UDP, relay overflow kills the relay's receiver

When the inbound pool is full, the UDP induct does not drop a single bundle and carry on. The code path is:

```
udpcli: bpBeginAcq -> bpContinueAcq (no ZCO space: non-blocking, returns "congestive", no ZCO)
        -> bpEndAcq: "[?] bpEndAcq called with no ZCO; dropping acquisition."  returns -1
        -> udpcli.c:120 "Can't acquire bundle."  -> ionKillMainThread -> induct shut down
```

From that moment the relay is **deaf**. It keeps forwarding what it already stores, but every later bundle sent to it is lost. UDP has no acknowledgement, so the senders still count those bundles as transmitted (`xmt`). The `[?] ZCO space is congested; discarding bundle.` path in `libbpP.c` is never reached on this convergence layer.

In `m4_overflow`, the induct died at T0+31.0. All 58 bundles sent before then were delivered, and all 32 sent after were lost (`events.csv`, `bundles.csv`). Delivery ratio was 0.644.

**Why this matters for M5/M6:** under vanilla ION, a dawn flush that overfills the relay does more than drop the excess. It **disconnects the relay for the rest of the run**, so the failure is a cliff rather than a gradual decline. Admission control that keeps relay inflow below capacity (LunaFlow's congestion policy) prevents exactly this. The finding is specific to the UDP convergence layer; LTP or TCP may behave differently, and that's worth one comparison run later.

**Measuring loss under this failure mode:** the relay never sees the lost bundles, so there's no per-bundle drop log. Count losses end-to-end (generated − delivered, in `bundles.csv`) and locate them with `induct_failures` together with `node_stats.csv` (sender `xmt` versus relay `rcv`).

## 8. Gotchas

| Symptom | Cause | Fix |
|---|---|---|
| A node hangs every admin command after an aborted tool | The tool was killed while holding an SDR transaction (seen with `bplist` under `timeout`) | `stop_all.sh` and reboot the scenario. The harness never kills ION tools mid-call except `bpsource` at the very end. |
| `New ZCO heap limit invalid!` in ion.log | A pool limit is larger than 40% of the heap | Use `buffer_mb` (it sizes `heapWords`), not hand-set `heap_words` |
| Flow rejected: `size > 60000` | UDP CL datagram limit | Use more, smaller bundles |
| Deliveries stop mid-run with no drop lines | Induct failure (§6) | Check `summary.json → induct_failures` |
| ion.log times are local time; contact plan times are UTC | ION formats each differently | The harness converts log stamps with `time.mktime` (local time) |
