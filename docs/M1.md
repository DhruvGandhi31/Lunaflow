# M1 — Two-Node ION Testbed (bping over UDP)

**Status: PASS** (Sep 2026, WSL2 Ubuntu). `bping` node 2 → node 3: 3/3 bundles, 0% loss, ~4.3 ms avg RTT.

**Goal:** prove the full toolchain works end-to-end: build ION from source, run two independent ION nodes on one machine, and round-trip bundles between them through the real BPv7 stack (contact plan → CGR routing → UDP convergence layer).

---

## 1. Build ION from source

```bash
git clone --depth 1 https://github.com/nasa-jpl/ION-DTN.git
cd ION-DTN
./enable_manual_build.sh --skip-clean   # switch to manual Makefiles (no autotools needed)
make all                                 # slow on WSL if repo is under /mnt/c — keep it in ~/
sudo make install && sudo ldconfig
which ionadmin bpadmin bping bpecho killm   # all must resolve
```

Notes:
- `bpversion` may not exist in this build — harmless, skip it.
- Build INSIDE the Linux filesystem (`~/`), never `/mnt/c/...` (5–10× slower).
- No-root alternative: collect binaries manually (`find . -path "*/x86_64-linux/bin/*" -exec cp {} ~/ion/bin \;` + libs, then export PATH/LD_LIBRARY_PATH).

## 2. What an ION "node" actually is

One node = a shared-memory data store (**SDR**) + ~10 daemons around it:
`rfxclock` (contact plan clock), `ipnfw` (forwarder/CGR), `ipnadminep` (admin endpoint), `bpclock`, `bptransit`, `bpclm`, `udpcli` (UDP induct = listener), `udpclo` (UDP outduct = sender).

Config files, in the order `ionstart` runs them:

| File | Program | Configures |
|---|---|---|
| `*.ionconfig` | (read by ionadmin) | shared-memory identity: `wmKey`, `sdrName`, `sdrWmKey` — **must be unique per node** |
| `*.ionrc` | `ionadmin` | node number (`1 2 amroc.ionconfig` = "init as node 2"), start daemons (`s`) |
| `global.ionrc` | `ionadmin` | the contact plan (shared by all nodes) |
| `*.ionsecrc` | `ionsecadmin` | security DB init (just `1`) |
| `*.bprc` | `bpadmin` | endpoints (`ipn:2.1`), UDP induct port, outducts to peers |
| `*.ipnrc` | `ipnadmin` (called from bprc) | egress plans: node number → `udp/127.0.0.1:port` |

## 3. Multi-node-on-one-host (the critical trick)

ION assumes one node per machine. Two things make N-nodes-on-one-host work:

1. **Unique shared-memory keys** per node (`wmKey`/`sdrName`/`sdrWmKey` in each `.ionconfig`) — so the nodes' memory regions don't collide.
2. **The `ion_nodes` registry**: `export ION_NODE_LIST_DIR=<parent dir>` — `ionadmin` writes each node's identity + directory path there, and every ION program figures out *which node it belongs to from its current working directory*. Run a tool from inside `n2/` → it's a node-2 tool.

## 4. Run it

```bash
mkdir -p ~/testbed/two_node && cd ~/testbed/two_node
cp -r ~/ION-DTN/tests/multinode-sdrwmkey/2.ipn.ltp .
cp -r ~/ION-DTN/tests/multinode-sdrwmkey/3.ipn.ltp .
export ION_NODE_LIST_DIR=$HOME/testbed/two_node   # ABSOLUTE path, in EVERY terminal
rm -f ion_nodes

for n in 2 3; do (cd $n.ipn.ltp && ionadmin amroc.ionrc && ionadmin global.ionrc \
  && ionsecadmin amroc.ionsecrc && bpadmin amroc.bprc); done

cat ion_nodes                       # expect 2 lines
ss -ulpn | grep -E "4556|4557"      # expect EXACTLY one udpcli per port

# terminal 2 (must also have ION_NODE_LIST_DIR exported):
cd ~/testbed/two_node/3.ipn.ltp && bpecho ipn:3.1
# terminal 1:
cd ~/testbed/two_node/2.ipn.ltp && bping -c 3 -i 1 ipn:2.2 ipn:3.1
```

Expected:

```
abcyzbcyz64 bytes from ipn:3.1  seq=0 time=0.006442 s
...
3 bundles transmitted, 3 bundles received, 0.00% bundle loss
```

Watch characters decode the round trip: `a` bundle created → `b` queued for forwarding → `c` transmitted via UDP → `y` echo accepted at far end → `z` reply delivered back.

## 5. Troubleshooting log (every failure I actually hit)

| Symptom | Root cause | Fix |
|---|---|---|
| `Can't get shared memory segment ... key = 65280 ; size = 0` right after startup | Follow-on admin programs couldn't find the node in `ion_nodes` → fell back to default keys → attached to nothing. `ION_NODE_LIST_DIR` unset/wrong in that shell. | Export it (absolute path to the PARENT dir) in the same terminal; verify with `echo $ION_NODE_LIST_DIR`; checkpoint: `cat ion_nodes` right after the first `ionadmin` — must have a line. |
| `Can't open ion_nodes file: .../3.ipn.ltp/ion_nodes` | Exported `ION_NODE_LIST_DIR=$PWD` while standing inside a node dir — it must point at the parent. | Always use the absolute parent path; add to `~/.bashrc`. |
| bping: 3 transmitted, 0 received, but `abc` chars show transmission worked | **Stale duplicate node instances** from earlier failed runs. `ss -ulpn` showed port 4557 bound by TWO `udpcli` processes — the old zombie instance ate the incoming bundles while bpecho was attached to the new one. | Full teardown: `killm f` (plain `killm` does node-only cleanup and leaves survivors!), then `rm -f /dev/shm/sem.ion*`, `rm -f ion_nodes`, check `ipcs -m` empty. |
| Everything weird after a crashed run | Leaked SysV shared memory / semaphores with mismatched sizes | Same reset ritual as above. |

**Reset ritual (memorize):** `killm f && rm -f /dev/shm/sem.ion* <testbed>/ion_nodes` then `ss -ulpn | grep 45` must be empty.

**Health check (before every experiment):** `cat ion_nodes` has one line per node; `ss -ulpn` has exactly one `udpcli` per port.

## 6. What M1 established

- The full BPv7/CGR/UDP pipeline runs on this machine, per-node isolated.
- The contact plan (`global.ionrc`) drives routing — M2 exploits this by putting a *gap* in it.
- WSL terminals share kernel + IPC; only environment variables are per-shell.
