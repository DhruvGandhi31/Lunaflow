# M3 — Scenario Generator: JSON → Full ION Network

**Status: PASS** (Sep 2026, WSL2).
Smoke test (6 nodes): 3/3 bundles from three probes crossed the coverage gap via the relay.
Scale test (17 nodes): all nodes registered (17/17), 170 contact entries applied network-wide from a single shared T0.

**Goal:** stop hand-writing ION configs. One JSON file describing the network (nodes, contact windows, rates, buffer caps) generates the entire runnable scenario — config tree, boot scripts, and a time-synchronized contact plan. Every later milestone (M4 harness, M5 dawn flush, M6 controller A/B) is "edit JSON, regenerate, run."

---

## 1. The files and how they fit together

```
scripts/genscenario.py      generator: scenario JSON -> config tree (run once per edit)
scripts/apply_contacts.py   contact-plan injector (copied into scenario dir; called by start_all.sh)
scenarios/m3_smoke.json     6-node validation scenario
scenarios/m3_full.json      17-node reference topology (the dawn-flush stage)
scripts/m3_smoke_run.sh     timed smoke experiment against m3_smoke

generated per scenario (e.g. ~/testbed/m3_full/):
  n<id>/...                 per-node ION config dir (6 files each, see §3)
  contacts.def              contact windows in RELATIVE seconds (input to apply_contacts)
  start_all.sh              boot all nodes, then apply the contact plan
  stop_all.sh               killm f + IPC cleanup
  scenario.json             copy of the input, for provenance
  t0.txt                    (at runtime) the shared T0 epoch — experiment scripts read this
```

## 3. genscenario.py in detail

**Input schema** (per `scenarios/*.json`):
- `duration` — scenario length in seconds. Periodic contacts repeat until this (or per-contact `until`).
- `owlt` — default one-way light time in seconds (per-contact override allowed).
- `nodes[]` — `id` (also determines UDP port and shared-memory keys), `type` (documentation + boot ordering), optional `heap_words` (**the relay SDR cap — this is the buffer-size lever M4/M5 calibrate to force overflow**).
- `contacts[]` — either *periodic* (`period`, `offset`, `duration`, repeats until `until`) or *explicit* (`windows: [[start,end],...]`), plus `rate` (bytes/sec) and `bidir` (default true — generates both directions).

**What it emits per node** (`n<id>/`):

| File | Role |
|---|---|
| `node.ionconfig` | shared-memory identity: `wmKey 70000+id`, `sdrName ion<id>`, `sdrWmKey 72000+id` (deterministic, collision-free, away from ION's 6528x defaults), `heapWords` (SDR size) |
| `node.ionrc` | `1 <id> node.ionconfig` (init as node id) + `s` (start daemons) |
| `ranges.ionrc` | OWLT entries for every link — time-invariant, so safely loaded at boot with relative times |
| `node.ionsecrc` | security DB init |
| `node.bprc` | endpoints `ipn:<id>.0–3`, UDP induct on port `4000+id`, one outduct per neighbor, watch chars on |
| `node.ipnrc` | egress plans: neighbor node number → `udp/127.0.0.1:<4000+nbr>` |

Neighbor sets (ducts + plans) are derived automatically from the contact list — a node gets an outduct/plan for exactly the nodes it has outgoing contacts with.

**What it deliberately does NOT emit into node configs: contact windows.** See §4.

**`start_all.sh` details:** boots relays/ground first (they're everyone's next hop), probes after; per-node logs in `n<id>/start.log`; prints registry count (`N/17`); then hands off to `apply_contacts.py`. Starts every run with the M1 reset ritual (`killm f`, clear `/dev/shm/sem.ion*`, delete `ion_nodes`).

## 4. apply_contacts.py — why contact loading is a separate runtime step

**The problem it solves:** ION's relative contact times (`+10`) are anchored to the moment each node's `ionadmin` loads them. Nodes boot sequentially (~1–3 s each), so with 17 nodes the first and last node would anchor ~30–50 s apart — the network would *disagree about when windows open*, and cross-node routes would silently miss their contacts. At 3 nodes (M2) the skew was tolerable; at 17 it is fatal.

**The solution:** boot everything first, then synchronize:
1. Read `contacts.def` (relative windows).
2. Pick one shared **T0 = now + lead** (lead defaults to 15 s; passed as `start_all.sh`'s first arg).
3. Convert every window to **absolute UTC** ION timestamps (`a contact 2026/09/12-15:09:50 ...`) in a single file `contacts_abs.ionrc`.
4. Run `ionadmin contacts_abs.ionrc` from inside every `n<id>/` directory (cwd selects the node) — the identical plan lands in all 17 nodes.
5. Write `t0.txt` so experiment scripts can schedule traffic relative to T0 (`wait_until $((T0+15))`).

**Verified output (17-node run):**
```
[apply_contacts] 170 contact entries -> 17 nodes, T0=1789225790 (2026/09/12-15:09:50 UTC)
```

**Why this matters beyond correctness:** injecting contact-plan changes into *live* nodes via `ionadmin` is precisely the actuator the M6 LunaFlow controller uses to enforce policy — staggering probe windows at dawn, throttling rates to match relay drain, deleting contacts of battery-dead nodes. M3 built the controller's write-path; M6 adds the decision logic.

## 5. The two scenarios

**m3_smoke (6 nodes):** relay 20, ground 30, probes 101–103, station 110. Window A (probes→relay, T0+10..40) and window B (relay→ground, T0+60..100) with a gap between — M2's story, but generated. Validation result: 3 parked at relay at T0+51, 0 at ground; 3/3 delivered by T0+112. **PASS.**

**m3_full (17 nodes) — the dawn-flush stage:** far side = probes 101–106 + station 110 through relay 20 (Queqiao-class); South Pole = habitat 210, landers 211–213, rovers 221–223 through relay 21 (ELFO-class); relay↔relay crosslink; staggered relay→ground downlinks (offsets 90 and 120 in a 240 s period ≈ one compressed orbit). Time compression convention: 1 real second ≈ 1 sim minute. Scale result: 17/17 registered, ~170 daemons, no memory strain. **PASS.**

## 6. Design invariants (rely on these later)

- `id` determines everything addressable: port `4000+id`, `wmKey 70000+id`, `sdrWmKey 72000+id`, endpoints `ipn:<id>.0–3`. No collisions possible if ids are unique (asserted).
- Regeneration is destructive: `genscenario.py` wipes and rebuilds the scenario dir. Never hand-edit generated configs — edit the JSON.
- `start_all.sh` is idempotent-ish: it force-resets the host first. Only one scenario can run at a time (shared `killm f`).
- Experiment scripts must read `t0.txt`, never assume T0.

## 7. Gotchas / troubleshooting

| Symptom | Cause | Fix |
|---|---|---|
| Registry shows < N nodes | a node's start failed | read its `n<id>/start.log` |
| Contacts seem ignored / no forwarding | experiment used its own clock instead of `t0.txt`; or plan applied before a node was up | always `start_all.sh` → `t0.txt`; check `[apply_contacts] ... -> N nodes` count matches |
| `apply_contacts` FAIL lines | `ionadmin` couldn't attach in that node dir | node not in `ion_nodes` (check registry), or env var missing in that shell |
| Weirdness after aborted run | leaked IPC | M1 reset ritual; `stop_all.sh` does it |
